# Verification

There are six UVM environments: three in SystemVerilog UVM 1.2, run in Vivado xsim, and three in pyuvm, run in cocotb on Verilator or Icarus. Each language has a block-level environment for the FPU, a top-level environment that drives the whole accelerator through its UART pins, and an Ethernet environment that drives it through its RMII pins (and the UART pins, for checks that mix the two). The two languages use different reference models on purpose. Each model is a second, independent reading of the specification for the other.

```
                    SV UVM (xsim)                           pyuvm (Verilator / Icarus)
FPU block   hw/tb/uvm/fpu   ref: C via DPI-C        hw/tb/pyuvm/fpu   ref: fp32ref.py (exact)
Top level   hw/tb/uvm/top   ref: SV device model    hw/tb/pyuvm/top   ref: DeviceModel (Python)
Ethernet    hw/tb/uvm/eth   ref: SV eth_ref_model   hw/tb/pyuvm/eth   ref: EthBoardModel (Python)
```

A seventh test, `hw/tb/sv/tb_nexys_eth.sv`, simulates the board top level with Xilinx's models of the clocking primitives (see [Board-level Ethernet test](#board-level-ethernet-test)).

The older directed checks still run: `hw/tb/sv/tb_accel_core.sv` (xsim) and `hw/tb/cocotb/test_accel_core.py` replay `hw/tb/vectors.py`, a list of request/reply byte strings generated by the Python device model.

## FPU block environment (`hw/tb/uvm/fpu`)

```
 sequences ─► fpu_sequencer ─► fpu_driver ──► fpu (DUT) ──► fpu_rsp_monitor ─┐
                                    │                                        ├─► fpu_scoreboard (DPI-C ref)
                                    └──────► fpu_req_monitor ────────────────┴─► fpu_coverage
```

* **fpu_if**: clocking blocks for the driver and monitors, a cycle counter, and SVA assertions. A waiting request must stay stable, and no X is allowed on outputs.
* **fpu_req_item**: `rand` op, operand classes (zero, subnormal, normal, near one, ∞, qNaN, sNaN, boundary, large, int-like, raw, related) with `dist` weights, and a random seed. `post_randomize()` builds the operand bits with `fp_lcg`.
* **fpu_driver**: assigns tags and drives back-to-back requests. `try_next_item` avoids re-sending a stale item, and the driver honours `req_ready` back-pressure from divide/sqrt.
* **fpu_scoreboard**: predicts each request through `fp_ref_eval` (DPI-C), matches responses by tag (results can return out of order), and compares result bits and flags exactly. It also checks latency: pipelined ops must take exactly 7 clocks, divide/sqrt at least 30, and nothing may be left outstanding at the end.
* **fpu_coverage**: covergroups on op × operand kind (× operand kind for two-input ops) and op × each flag.
* **Sequences** (`fpu_seq_lib.svh`):

| sequence | purpose |
|---|---|
| `fpu_rand_seq` | constrained random through `randomize()` |
| `fpu_lcg_seq` | deterministic stream from the shared LCG |
| `fpu_corner_seq` | every op on every pair of 28 special values |
| `fpu_tie_seq` | ADD/SUB where b is ½, ¼ or 1 ulp of a, to exercise ties to even |
| `fpu_mix_burst_seq` | DIV/SQRT followed by bursts of pipelined ops, to exercise the result merge and out-of-order tags |
| `fpu_underflow_seq` | operands near 2^-126 |

* **Tests**: `fpu_smoke_test`, `fpu_corner_test`, `fpu_rand_test`, `fpu_lcg_test`, `fpu_stress_test` (two sequences in parallel on one sequencer), and `fpu_regress_test`.

## Top-level environment (`hw/tb/uvm/top`)

Layered sequencers, from protocol commands down to UART bytes:

```
cmd sequences ─► cmd_sequencer (no driver)
                     ▲  get_next_item / item_done
                     │
             cmd_to_uart_seq (layering sequence, COBS + CRC, lock() per frame)
                     │
raw_bytes_seq ─► uart_sequencer ─► uart_driver ─► uart_rx pin ─► accel_core
                                                                    │
         uart_frame_monitor (rx wire) ─► top_scoreboard ◄── uart_frame_monitor (tx wire)
                                         (SV device model + DPI-C FPU)
top_vsequencer: handles to cmd_sequencer and uart_sequencer for virtual sequences
```

* Command sequences act like a real host. Each one sends a command, then waits for the reply through a TLM analysis FIFO in `cmd_sequencer`, with a timeout. A deliberately corrupted command waits and checks that no reply comes back.
* The layering sequence `lock()`s the UART sequencer for each frame, so `raw_bytes_seq` (used to inject malformed COBS) can never split a frame.
* `top_ref_model` takes the raw bytes of every frame the DUT received, decides whether the DUT must stay silent (link errors) or reply, and builds the exact reply wire bytes: COBS, CRC, status, data, cycle counts, and FPU results through DPI. The scoreboard compares the observed bytes against that prediction.
* The virtual sequence `top_regress_vseq` runs smoke, memory, FPU-kernel (all 12 ops) and error sequences, injects COBS garbage and an empty frame, and checks that the link still works afterwards.

## pyuvm mirrors (`hw/tb/pyuvm`)

These are the same structures written with pyuvm's `uvm_sequencer`, `uvm_driver`, `uvm_monitor`, `uvm_tlm_analysis_fifo` and `uvm_subscriber`. The differences are deliberate or forced by the tools:

* The references are `fp32ref.py` and `DeviceModel`, not the C and SV models.
* pyuvm has no `lock()`/`grab()`. The UART sequencer holds a cocotb `Lock` that the layering sequence and raw sequences take for each frame.
* cocotb has no clocking blocks. Drivers change inputs on the falling edge, and monitors sample in `ReadOnly` after the falling edge.
* Coverage is counted in Python dictionaries.

## Ethernet environment (`hw/tb/uvm/eth`)

```
eth cmd sequences ─► eth cmd_sequencer ─► cmd_to_eth_seq (COBS/CRC frame in UDP/IPv4/Ethernet + FCS)
raw frame sequences (ARP, ping, junk) ─┐          │
                                       ▼          ▼
                              rmii_sequencer ─► rmii_driver ─► rmii_phy_if (PHY model) ─► RMII rx pins
uart cmd sequences ─► uart cmd_sequencer ─► cmd_to_uart_seq ─► uart agent ─► UART rx pin      │
                                                                                         accel_core
RMII rx pins ─► rmii_rx_monitor ─┐                                                            │
RMII tx pins ─► rmii_tx_monitor ─┼─► eth_scoreboard (eth_ref_model + top_ref_model) ◄── UART monitors
               │                 │
               └─► udp_reply_extractor ─► eth cmd_sequencer reply FIFO
```

* The environment imports `top_uvm_pkg` and reuses its command items, `cmd_sequencer`, command sequences, UART agent and `top_ref_model` without changes. The new parts sit below the command layer.
* **rmii_phy_if** (`hw/tb/common`) is the PHY model, written as an interface with tasks so that both the UVM driver and the plain board-level test can use it. `send_frame` drives RXD/CRS_DV/RX_ER the way the LAN8720A does. Outputs change `tco` after the rising reference clock. CRS_DV can rise a few dibits before the preamble with RXD = 00, the preamble can be shortened, and CRS_DV can toggle during the last nibbles (as the PHY does while its FIFO drains). RX_ER can be raised for one dibit, and the gap after a frame can be set. On the transmit side it checks setup (4 ns) and hold (1.5 ns) of TXD/TX_EN at every reference-clock edge, and `recv_frame` returns a transmitted frame after checking its preamble.
* **eth_frame_item** carries the frame bytes and the PHY knobs. The knobs are `rand` with weighted `dist` constraints, so most frames are ordinary and some use each unusual PHY behaviour.
* **rmii_rx_monitor** rebuilds received frames from the pins with the rule a MAC must use: a dibit counts while CRS_DV is high now or was high one sample ago. It also records what the PHY did (lead-in dibits, preamble length, toggled nibbles, RX_ER) for coverage. **rmii_tx_monitor** checks each transmitted frame: 7 × 0x55 + 0xD5, whole bytes, a good FCS, at least 64 bytes, and at least 48 clocks (96 bit times) of idle before the next frame.
* **eth_ref_model** predicts the exact reply frames, FCS included, with its own SV CRC-32, checksums and frame builders (`eth_codec.svh`). It hands command frames to `top_ref_model`. The scoreboard has one model for both transports, so a word written over UDP and read over UART, and the summed STATUS counters, are predicted the way the hardware behaves.
* **Coverage**: received frame kind (ARP, ping, UDP, ignored, receive error, drop) × CRS_DV toggling, plus lead-in, short preamble and RX_ER.
* `eth_regress_vseq` runs: ARP; pings with 0, 1, 32, 333 and 1472 data bytes; the smoke, memory, FPU (all 12 operations) and error sequences over UDP; junk traffic (mDNS to a multicast MAC, IPv6, broadcast NetBIOS, wrong port, wrong IP, ARP for another address, a gratuitous ARP reply, IPv4 options, a fragment, a bad FCS, a runt, an oversized frame); a frame with RX_ER; two frames in one datagram with the second unterminated; two datagrams back to back; writes on one transport read back on the other; and STATUS over UDP after UART errors.

The pyuvm mirror (`hw/tb/pyuvm/eth`) has the same structure. Its PHY model is the Python class `RmiiPhy`, and its reference is `EthBoardModel` (`sw/mathaccel/net/board_model.py`) wrapped around `DeviceModel`. It has three tests: `EthSmokeTest`, `EthRegressTest` (the scenario list above, PHY knobs chosen from `--seed`) and `EthMultiTest` (multi-frame and back-to-back datagrams on their own).

## Board-level Ethernet test

`hw/tb/sv/tb_nexys_eth.sv` simulates `nexys_top` with the unisim models of the MMCM, BUFGs and ODDR, so it covers what the accelerator-level environments cannot: clock generation, the forwarded 50 MHz ETH_REFCLK with its 321.75° phase shift, and the PHY reset sequence (shortened for simulation by the `PHY_RST_BITS` parameter). The PHY model is clocked by ETH_REFCLK after a modeled 4.5 ns pad and trace delay. The transmit pins reach it with the same delay, and its outputs (10 ns after its clock edge) reach the FPGA 1 ns later. The test checks the REFCLK period and exchanges ARP, a ping, a UDP PING and a UDP FILL. It compares every reply byte with `eth_ref_model`, then sends a PING over the real 2 Mbaud UART. With the 321.75° phase the PHY's setup/hold checks report nothing. As a check on the checker, setting the phase to 180° (which puts the PHY's clock edge on top of the transmit data) gives 594 setup violations.

These delays are rough numbers, not a timing analysis. The real check of the RMII interface is Vivado's, with the LAN8720A's timing written into the XDC.

## Seeds and reproducing failures

`sw/mathaccel/fpgen.py` (Python) and `fp_lcg` in `hw/tb/uvm/common/fp_common_pkg.sv` (SV) are line-for-line twins of one 32-bit LCG. The same seed produces the same `(op, a, b)` stream in both languages. Both sides check themselves against pinned values (`fp_lcg::selftest()` and `test_generator_is_deterministic`), so a failing LCG seed from xsim can be replayed in pyuvm and the reverse. Constrained-random runs in xsim are reproduced with `--seed` (xsim `-sv_seed`).

## Board results

I ran these checks on 2026-10-13 on a Nexys A7-100T over USB-UART on COM3 at 2 Mbaud. The programmed bitstream came from `hw/scripts/build.tcl`. The implementation timing report met the 100 MHz constraint with WNS +0.578 ns; the results below came from tests on the physical board.

| check | command | result |
|---|---|---|
| identity | `mathaccel --port COM3 ping` | magic OK, v0.2, 65,536 words, 100 MHz |
| full scratchpad | `mathaccel --port COM3 memtest --words 65536` | all 65,536 words read back correctly; 0 mismatches |
| kernel timing | `mathaccel --port COM3 bench` | FILL 4,096 words = 4,097 cycles, matching the Python model |
| single operations | individual `mathaccel --port COM3 fp` commands | all 9 cases checked by hand gave the expected answers |
| FPU on hardware | `mathaccel --port COM3 fptest --n 5000` | 5,000 vectors per operation, 60,000 total; 0 result or flag mismatches against the Python model |
| device tests | `pytest sw/tests/test_device.py --port COM3` | 23 passed: 20 board tests and 3 simulator-only tests |
| link errors afterwards | `mathaccel --port COM3 status` | 0 CRC errors, 0 frame errors |

The FPU kernel reported 4 clocks per element for the pipelined operations and 33 for divide and square root. Those counts describe the kernel on the FPGA. They exclude the time spent sending operands, receiving results, and checking the Python reference on the host.

One correction to the hand-checked expectations: `10^-30 * 10^-20` is too small to survive binary32 rounding, including as a subnormal. The correct result is positive zero (`0x00000000`) with UF and NX set (`0b00011`). That is what the board returned, and the Python model agrees. An exact subnormal result would have neither flag; this product rounds to zero and is inexact.

The device tests taking the `dev` fixture used COM3. Three tests create `SimTransport` themselves: corrupted-frame counters, neighboring-word preservation, and invalid payload length. Supplying `--port COM3` does not move those tests onto the board. The million-vector-per-operation results described in [numerics.md](numerics.md#verification-evidence) are separate simulation evidence; the hardware run here used 5,000 vectors per operation.

### USB serial latency: before and after

With the FTDI driver's default 16 ms latency timer, the measured NOP round trip was 15.976 ms. I changed the timer to 1 ms in Device Manager and repeated the checks. Full-memory readback, FILL timing, single-operation checks, all 60,000 FPU vectors, and the 23 device tests passed again, with no CRC or framing errors afterwards.

| measurement | 16 ms timer (default) | 1 ms timer | measured improvement |
|---|---|---|---|
| NOP round trip, averaged over 50 requests | 15,976 µs | 994 µs | about 16.1× faster |
| memory payload transfer rate, write plus read | 53 kB/s | 143 kB/s | about 2.7× higher |
| `fptest` wall time **per operation**, 5,000 vectors | about 1.9–2.1 s | about 0.63–0.74 s | roughly 3× faster, depending on the operation |
| FPU correctness | 60,000 vectors, 0 mismatches | 60,000 vectors, 0 mismatches | results and flags unchanged |

`bench` measures request round trips using host wall time. `memtest` reports the bytes written and read divided by elapsed time, excluding packet overhead from the byte count. `fptest` prints one wall-time measurement per operation; the ranges above are not the duration of the entire 12-operation run. Its elapsed time includes transfers and reference checks.

The shorter timer reduced the USB serial wait and closely matched the expected 1–2 ms round trip. It did not change the FPGA clock or the kernel cycle counts.

To repeat the comparison on Windows:

1. Open Device Manager and select **USB Serial Port (COM3)**, then **Properties**.
2. Open **Port Settings**, then **Advanced**, and set **Latency Timer** to **1 ms**.
3. Rerun `mathaccel --port COM3 bench`, `mathaccel --port COM3 memtest --words 65536`, `mathaccel --port COM3 fptest --n 5000`, `pytest sw/tests/test_device.py --port COM3`, and `mathaccel --port COM3 status`.

Use the board's actual port name if Windows assigns a different COM number.

## Ethernet board results

I tested the Ethernet transport on 2026-10-21. The board was the Nexys A7-100T, with its USB cable still connected for power, programming and the UART on COM3. A Cat 8 cable ran straight from the board's RJ45 jack to the laptop's Realtek Gaming 2.5GbE port (RTL8125, in a Gigabyte AORUS 15P YD running Windows 11), set to 192.168.10.1/24. The first bitstream met timing with WNS +0.195 ns and WHS +0.036 ns. The RMII paths had 1.85/1.78 ns (receive setup/hold) and 2.48/9.99 ns (transmit setup/hold) of slack. The final bitstream adds the debug LEDs described below and met timing with WNS +0.118 ns and WHS +0.082 ns.

### Results

| ARP | the laptop learned 02-4d-41-43-43-01 for 192.168.10.2 |
| ping | 4/4 replies, under 1 ms |

| `fp div 1 3` over UDP | 0x3EAAAAAB, NX set, 39 kernel cycles, same as the Python model |
| FPU on hardware over UDP | 5,000 vectors per operation, 60,000 total, in 2.4 s; 0 result or flag mismatches |
| link errors afterwards | 0 CRC errors, 0 frame errors, read over both UDP and UART |

| measurement | UART (COM3, 1 ms FTDI timer) | UDP | |

The UART and UDP NOP numbers come from the same run, 2,000 requests each. Like the UART measurements above, these are host wall-clock times: they include Python, the Windows network stack and the link, while the FPGA's NOP kernel itself takes one clock. The 873 kB/s counts payload bytes only; the driver still sends one request and waits for its reply before sending the next.

### Link and laptop settings

The link did not come up at first. The board's RJ45 LEDs lit, but Windows reported the cable as disconnected. It came up at 100 Mbit/s full duplex once I disabled Green Ethernet, Power Saving Mode and Gigabit Lite in the Realtek adapter's advanced properties and replugged the cable at the laptop end. Each time a settings change reset the adapter, the link stayed down until I replugged the cable; the FPGA side does not notice the lost link and restart the PHY.

### Delayed replies: the laptop, not the board

The first full run passed every check, but the NOP round trip had a 99th percentile of 5.0 s, the driver's timeout for kernel commands. About 1 in 190 replies arrived late. I narrowed it down in three steps:

1. With a 50 ms timeout and no retries, every late reply still arrived eventually, with the right tag. The board was not losing replies.
2. With a 6 s timeout, a late reply did not arrive at all until the laptop sent another request. Then it came in 0.3 ms later, followed by the reply to the new request, and from then on every reply was one behind. When I sent UDP WRITE_MEM requests and read the memory back over the UART during a stall, the new value was always there. The board had executed the request; only its reply was missing. A UART command during the stall did not release it.
3. I added debug LEDs to the bitstream. LED12 to LED14 latch if the reply buffer, the transmitter or the replay engine stays busy for more than 10 ms; a reply normally leaves within about 0.1 ms. After about 50 stalls, the longest 3.7 s, all three were still dark, and so were LED5 and LED6. The board had sent every reply within 10 ms. The laptop's receive counters showed 8,162 frames with 0 discarded and 0 errors.

So the laptop's network adapter held received frames until the next frame arrived. Changing its settings narrowed it down:

| laptop configuration | late replies |
|---|---|
| driver 10.47.121.2021, default settings | 26 in 5,000 (also 4 in 2,000, and 19 in 2,000 with a 200 µs pause between requests) |
| Interrupt Moderation disabled | 26 in 5,000 |
| Receive Side Scaling disabled as well | 1 in 5,000, then 1 in 20,000 |
| driver updated to 10.80.50.407 (Realtek, 2026-04-07), Interrupt Moderation and Receive Side Scaling still disabled | 0 in 10,000 |

With the new driver the median NOP round trip was 88 µs and the slowest of the 10,000 took 1.98 ms. The 99th percentile was 986 µs, higher than the 234 µs with the old driver; I have not looked into why. The driver update turned Green Ethernet, Gigabit Lite and Power Saving Mode back on, and the link stayed up with them on. I did not test the new driver with Receive Side Scaling turned back on.

### Still open

* After the laptop's adapter resets, the link only comes back when the cable is replugged. A fix would read the PHY's link status over MDIO and reset the PHY if the link stays down.
* The debug LEDs are still in the design. LED8 to LED11 show live state (transmitter busy, reply waiting in the reply buffer, replay engine inside a datagram, reply still in the encoder); LED12 to LED14 are the latching versions of the first three. Pressing the CPU reset button clears them.
* `pytest sw/tests/test_device.py --port udp:192.168.10.2` has not been run on the board yet; the bring-up script covers the same commands.

## Ethernet bring-up checklist

These are the steps for bringing up the Ethernet link on a new laptop or after changes, in order, so a failure points at one layer. [Ethernet board results](#ethernet-board-results) shows what happened the first time. After step 2, `python hw/scripts/eth_bringup.py --uart COM3` runs steps 3 to 6 by itself, stops at the first layer that fails with a hint, and writes the results to `build/eth_bringup_<time>.md`. `--port udpsim` dry-runs the script without a board.

1. **Laptop address.** The Realtek port needs a fixed address because nothing on a direct cable hands one out. In Settings → Network & internet → Ethernet → IP assignment → Edit, choose Manual, IPv4 on, address 192.168.10.1, subnet mask 255.255.255.0, no gateway, no DNS. The same from an administrator PowerShell, with the adapter name `ipconfig` shows:

   ```
   netsh interface ipv4 set address name="Ethernet" static 192.168.10.1 255.255.255.0
   ```

   On the Realtek Gaming 2.5GbE port, also disable Green Ethernet, Power Saving Mode and Gigabit Lite (Device Manager → adapter → Advanced, or `Set-NetAdapterAdvancedProperty`); without that the link did not come up on the first test. Disabling Receive Side Scaling, or updating the driver, removed the delayed replies described in the results.

   Windows will call the link "Unidentified network" and put it in the Public firewall profile. Replies to datagrams the laptop sent first are allowed through by default, so `mathaccel` needs no firewall rule; `ping` may need ICMP echo allowed in that profile if Windows blocks it.
2. **Program and link.** Program the board (`vivado -mode batch -source hw/scripts/program.tcl`). LED7 should come on within a few milliseconds (PHY out of reset), the RJ45 link LED should light within about two seconds, and `Get-NetAdapter` should show the port up at 100 Mbps. The PHY autonegotiates, so the 2.5 GbE port settles at 100 Mbit/s full duplex.
3. **ARP and ping.** `ping 192.168.10.2`, then `arp -a` should list 02-4d-41-43-43-01 for that address. LED3 and LED4 flash for each frame in and out; LED5 or LED6 on means a bad or dropped frame.
4. **Commands over UDP.** `mathaccel --port udp:192.168.10.2 ping`, `status`, `bench`, `memtest --words 65536`, `fp div 1 3`, `fptest --n 5000`, then `pytest sw/tests/test_device.py --port udp:192.168.10.2`.
5. **UART still works.** Repeat `ping` and `status` on the COM port. STATUS on either transport reports the same summed counters.
6. **Measure.** Record the NOP round trip and memory transfer rate from `bench` and `memtest` next to the UART numbers above.

If step 3 fails with the link up, the likely suspects are the RMII timing (the REFCLK phase in `nexys_top.sv` and the delays in the XDC) and the PHY strap pins; LED5 lighting on every ping points to receive timing.

## Tool issues found along the way

These are worked around in the code, with a comment at each spot:

| tool | problem | workaround |
|---|---|---|
| xelab 2023.2 | crashes on an inline constraint combining a sequence variable with an enum cast | `fpu_rand_seq` uses two `randomize()` calls and `local::` |
| xelab 2023.2 | writes each DPI call's source path into a C string, and `C:\Users` contains the invalid escape `\U` | `run_uvm.py` passes forward-slash paths |
| Vivado `.bat` tools | `cmd.exe` splits arguments at `=`, breaking `-testplusarg NAME=value` | plusargs are quoted on Windows |
| xsc (MinGW gcc 6.2, `-O0`) | `<`/`<=` compile to quiet compares; libm `sqrtf` of a negative returns the input | the C reference states those IEEE rules explicitly; pytest builds the C model with the same compiler and flags |
| Icarus Verilog | an expression in a port connection (`.in_sub(req_op == FOP_SUB)`) evaluated to X | named wires in `fpu.sv` |
| Icarus Verilog | needs an explicit cast for `?:` between enum values | `if`/`else` in `kernel_engine.sv` |
| Verilator | 2-state, so it cannot show X | the pyuvm monitor reports X/Z explicitly. Icarus (4-state) found the port-expression bug above |
| Icarus Verilog | crashes (`assign_to_lvector`) on `'{a, b}` assigned to an unpacked-array output port | two separate assignments in `eth_rx.sv` |
| xsim 2023.2 | kernel crash on a `fork` inside a `foreach` inside a `fork` in a task | `tb_nexys_eth` collects frames in a free-running receiver instead |
| SystemVerilog | a virtual interface must have the same parameter values as the instance it points to | the PHY model's timing values are variables, not parameters |
